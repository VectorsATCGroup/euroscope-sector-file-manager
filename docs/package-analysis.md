# Package Analysis — AeroNav SBXX Sector File Packages

This document records what was **actually discovered** by inspecting real material, and
carefully separates **Observed** facts from **Inferred** reasoning and **Unknown** gaps.
It is the empirical basis for the installer/updater engine.

## 1. Archive format — **Observed**

- Container is **7-Zip (`.7z`)**, not ZIP. `file` reports *"7-zip archive data, version 0.4"*.
- Package file name grammar:
  `` <FIR>-<Install|Update>-Package_<TS>-<AIRAC>-<REV>.7z ``
  - `<TS>` = 14-digit build timestamp `yyyyMMddHHmmss` (e.g. `20260810143935`).
  - `<AIRAC>` = 6 digits `YYMMRR` where `YYMM` is the AIRAC cycle and `RR` a revision (`260801` → cycle **2608**, rev **01**).
  - `<REV>` = 4-digit package revision (`0001`).
- Versioned sector files inside share the grammar: `<FIR>-<FIR>_<TS>-<AIRAC>-<REV>.sct` / `.ese`.

**Implication:** the AIRAC cycle and build timestamp are recoverable purely from file names — no need to
parse file bodies to identify a package's version.

## 2. Install package structure — **Observed**

Extracting an Install package yields exactly the layout of an installed FIR folder
(`Vatbrz/<FIR>/`). For SBBS:

```
SBBS-SBBS_<stamp>.ese                 ← versioned sector data
SBBS-SBBS_<stamp>.sct                 ← versioned sector geometry
sbbs_radar.prf                        ← EuroScope profile (radar)
sbbs_solo.prf                         ← EuroScope profile (solo/training)
aeronav_copyright.txt
SBBS/                                 ← nested data folder
├── aeronav_copyright.txt
├── Alias/alias.txt
├── ASR/{APP,CTR,R_TWR,TWR}/*.asr     ← screen layouts per position
├── ICAO/{ICAO_Aircraft,ICAO_Airlines,ICAO_Airports}.txt
├── NavData/{airway,icao,isec}.txt
├── Plugins/
│   ├── DiscordEuroscope.dll  RDFPlugin.dll  VCH.dll
│   ├── DiscordEuroscope_RadioCallsigns.txt
│   └── vATIS/vATIS-Profile-SBBS.json
└── Settings/
    ├── AircraftPerformance.txt  VoiceChannels.txt  login_profiles.txt
    ├── RADAR/{symbology,tags,general_settings,screen_layout,…}.txt
    └── SOLO/{symbology,tags,general_settings,screen_layout,…}.txt
```

- **`.rwy` is NOT present** in either package. The installed folders contain a `.rwy`, so it is
  **Inferred** to be generated by EuroScope at first load. The updater therefore never expects `.rwy`
  in a package and treats an installed `.rwy` as a derived artifact.
- Only binary payload is the three plugin **`.dll`** files (Install only). **No `.exe/.bat/.cmd/.ps1`
  scripts** exist in either package (safety-scanned). The updater never executes package contents.

## 3. Update package structure vs. Install — **Observed**

Normalizing the AIRAC-stamped names and comparing the two archives:

- **41 update files ⊂ 66 install files.** Every one of the **39 files common** to both archives is
  **byte-identical** (same AIRAC). The Update package is a strict content subset of the Install package.
- **Files the Update package OMITS** (i.e. present only in Install → *never written by an update*):

  | Omitted by Update | Interpretation |
  | --- | --- |
  | `Settings/RADAR/*` (10 files) | Per-controller radar customization |
  | `Settings/SOLO/*` (10 files) | Per-controller solo/training customization |
  | `Plugins/DiscordEuroscope.dll`, `RDFPlugin.dll`, `VCH.dll` | Binary plugins |
  | `<fir>_radar.prf`, `<fir>_solo.prf` | EuroScope profiles (user session state) |

- **Files the Update package INCLUDES** (refreshed each AIRAC): the versioned `.sct/.ese`, all
  `ASR/*.asr`, `Alias/alias.txt`, `ICAO/*`, `NavData/*`, `Plugins/DiscordEuroscope_RadioCallsigns.txt`,
  `Plugins/vATIS/vATIS-Profile-<FIR>.json`, and three loose `Settings/` files
  (`AircraftPerformance.txt`, `VoiceChannels.txt`, `login_profiles.txt`), plus `aeronav_copyright.txt`.

## 4. Personalization preservation — **Observed + confirmed by user**

Cross-AIRAC diff of the real snapshots (2603 → 2607) confirms the model end-to-end:

| File group | 2603 vs 2607 | Meaning |
| --- | --- | --- |
| `Settings/RADAR/symbology.txt`, `tags.txt`, `Settings/SOLO/general_settings.txt` | **identical** | Personalization — untouched across updates |
| `NavData/airway.txt`, `NavData/isec.txt`, `ICAO/ICAO_Airports.txt`, `Alias/alias.txt` | **differ** | AIRAC data — refreshed by updates |

> The division confirmed: *"the files we usually personalize are in the `Settings` folder, and the
> update package doesn't overwrite them because it doesn't contain them."*

**Adopted engine rule (safe and faithful):**
> **An Update applies exactly the set of files contained in the Update package, overwriting them, and
> never deletes or modifies any file that is not in the package.**

This preserves personalization *by omission* — the package itself is the source of truth. No
hardcoded "personalization file list" is invented (a hardcoded list would silently rot when AeroNav
changes packaging). The engine additionally treats the versioned sector files specially — see §5.

> **Caveat surfaced to users:** the Update package *does* refresh three loose `Settings/` files
> (`login_profiles.txt`, `VoiceChannels.txt`, `AircraftPerformance.txt`). A controller who hand-edits
> those will see them replaced by an update — exactly as the official manual flow does. The mandatory
> pre-update backup (see the engine) always captures them, so nothing is unrecoverable.

## 5. Versioned sector files & the `.prf` re-point — **Observed → Inferred**

- **Observed:** `<fir>_radar.prf` contains `Settings⇥sector⇥\<FIR>-<FIR>_<stamp>.sct`, referencing the
  sector file **by its exact stamped name**.
- **Observed:** across the three snapshots the `sector` reference changed to each new stamped name, and
  the FIR folder never accumulated old sector files (always exactly one `.sct` + `.ese` + `.rwy`).
- **Observed:** the `.prf` otherwise carried the user's own `LastSession` values forward (callsign,
  range, ATIS text differed per snapshot), i.e. the profile was *not* wholesale replaced between AIRACs.
- **Inferred (mechanism unconfirmed):** applying an Update therefore must (a) remove the previous
  stamped `.sct/.ese/.rwy`, and (b) surgically rewrite only the `sector` line of each existing `.prf`
  to point at the new `.sct`, leaving every other profile line intact. The engine does exactly this.
  The *official* tool's mechanism for (b) — manual, provider-driven, or automatic — is **Unknown**.

## 6. AIRAC / version indicators — **Observed**

- Authoritative version for a package or an installed FIR: the `<AIRAC>` segment (`YYMMRR`) of the
  versioned `.sct/.ese` file names (and of the package name). Cycle comparison is a simple `YYMM`
  ordinal compare; `RR` breaks ties within a cycle.
- A freshly-updater-installed FIR additionally records a `manifest` (`state.json`) with the AIRAC,
  build timestamp, package type and per-file SHA-256, giving high-confidence status later.
- Manually-installed legacy folders have **no manifest**; version is still recoverable from the
  stamped sector file name, but modification state is not — such installs report
  **"Installed — version unknown"** until the updater performs an operation.

## 7. Open questions — **Unknown**

1. Exact official mechanism that re-points the `.prf` `sector` line on update (see §5).
2. Whether AeroNav ever *deletes* a data file between AIRACs (none observed; the by-omission rule
   means the updater would leave an orphaned data file behind — considered acceptable and safe, and
   logged if detected via manifest diff).
3. Whether `<REV>`/`<TS>` ever advance without an AIRAC cycle change (would appear as a same-cycle
   update; handled by comparing full `AIRAC-REV-TS`).
4. Package `.7z` compression method variants across FIRs (only LZMA-family observed; the extractor
   uses SharpCompress which covers the 7z method set AeroNav is known to use).
